## Data model and access

- `lead_sources` (org, `key`, name, active): seeded for the default org as `manual`, `test`, `website` (active) and
  `google`, `facebook` (inactive until their connectors exist). A lead's `(org_id, source)` must reference a source.
- `leads`: contact fields as given plus `email_norm` and `phone_norm`; product/interest, message, branch,
  `assigned_to`, `status` (`new | contacted | quoted | won | lost | spam`), `gclid`, `fbclid`, `utm`, `duplicate_of`,
  the routing rule used, the Xero match (Xero ids, numbers, totals and currency codes), the raw payload and a
  generated `search_text`. `(org_id, source, external_id)` is unique, so a source id lands only once.
- `lead_events`: `created`, `duplicate`, `routed`, `emailed`, `matched`, `status`, `assigned`, `note`. `meta` holds ids,
  keys and field names only; the text of a staff note lives in `body`. `org_id` always comes from the lead (trigger).
- RLS: org members with role admin or staff read leads and events; reviewers and other orgs see nothing. Members read
  `lead_sources`; only admins read `routing_rules`. No client role can write any of these tables: every write is a
  server action or the intake endpoint using the service role after its own check.
- `email_log.lead_id` ties a notification to its lead; `org_id` is taken from the lead.
- `xero_contacts.email_norm` (generated) and `xero_contacts.phone_norm` (trigger: first phone of `raw.Phones`, MOBILE
  then DEFAULT, last 9 digits) are derived match keys; the M2 sync does not write them.

## Rules

- **Normalisation** (as the Make Gravity flow): email lower-cased and trimmed; phone digits only, last 9 digits
  (`+27 82 555 0101`, `082 555 0101` and `0027825550101` all give `825550101`). Fewer than 9 digits is ignored.
- **Duplicates**: another lead in the same org with the same normalised email or phone. `duplicate_of` points at the
  earliest one (or that lead's own original). Duplicates still land, route and notify; they are flagged in the list
  ("Duplicates only" filter), on the lead page and in the email body.
- **Routing**: active rules ordered by `priority` (lowest first, then oldest). A rule matches when every set condition
  holds: `match_source` (equals the source key), `match_product` (keyword contained in the product text, any case),
  `match_branch` (equals the lead's branch, any case). The first match may set `assign_branch` and names the
  notification key `notify_event_key` (`leads.<something>`). No match: `leads.new`. Seeded: one catch-all rule at
  priority 1000 to `leads.new`.
- **Recipients**: `notification_recipients` rows for the routed key. A key with no active inbox falls back to
  `leads.new` (seeded to sales@). To route Durban tanker leads, for example, add a rule
  `match_product = 'tanker', match_branch = 'Durban', notify_event_key = 'leads.durban'` and recipients for
  `leads.durban`. There is no rules editor yet: rules and recipients are added by an admin in SQL (service role).
- **Xero matching** (BUILD_PLAN 4.7): the lead's `email_norm` or `phone_norm` equals a mirrored contact's. Quotes count
  when their status is SENT, ACCEPTED, DECLINED or INVOICED; the latest by quote date is shown. Invoices count when
  they are sales invoices (ACCREC), not DELETED or VOIDED, dated on or after the start date and with a total greater
  than 0; the latest is shown and the running total is the sum in the latest invoice's currency (currencies are never
  added together). The start date is `app_settings` key `leads.invoice_match_from` (`"YYYY-MM-DD"`), default
  `2026-10-01`.
- **Re-matching**: matching runs when a lead is created. "Re-match open leads with Xero" on `/admin/leads` (admins:
  `integrations.manage`) re-runs it for every lead with status new, contacted or quoted, for up to 20 s, and queues the
  rest as an outbox job `leads.rematch` (`{ from: <offset> }`). Enqueue the same job from a schedule, or after a Xero
  sync, to keep matches current. A lead is written, and a `matched` event logged, only when its match changed.
- **Notifications**: only intake posts send one (subject "New lead from <source> (<branch>)", no personal data; the
  body holds the details and a link to the lead). Manual leads are routed and matched but do not email, because the
  person entering the lead already has it.

## Posting a test lead

Set `LEADS_WEBHOOK_SECRET` (at least 32 characters, e.g. `openssl rand -hex 32`). If it is unset or shorter, the
endpoint answers 503 to everything.

```bash
curl -sS -X POST "$APP_URL/api/webhooks/leads" \
  -H 'content-type: application/json' \
  -H "x-leads-secret: $LEADS_WEBHOOK_SECRET" \
  -d '{
    "source": "test",
    "source_id": "test-0001",
    "form": "Product Inquiry",
    "name": "Test Person",
    "email": "test.person@example.invalid",
    "phone": "+27 82 555 0101",
    "product": "Fuel trailer",
    "branch": "Durban",
    "message": "Synthetic test lead",
    "gclid": "test-gclid",
    "utm": { "utm_source": "test" }
  }'
# {"ok":true,"duplicate":false}   (posting the same source_id again: {"ok":true,"duplicate":true})
```

| Field | Rule |
|---|---|
| `source` | `test` or `website` (manual leads come from the inbox) |
| `source_id` | required, 1 to 200 chars; the idempotency key with `source` |
| `email` / `phone` | at least one (phone needs 9+ digits); email must be valid |
| `name`, `product`, `message`, `form`, `branch`, `gclid`, `fbclid` | optional text with length caps; branch letters, spaces, `.'-` |
| `utm` | optional object of `utm_*` keys to strings |

Responses: 200 `{ ok, duplicate }`; 400 `{ error, fields }` (field names only); 401 wrong or missing secret; 413 body
over 64 KB; 429 more than 60 posts a minute from one client; 503 not configured; 500 processing failed (the raw event
is kept as `failed`, and a retry of the same `source_id` finishes it).

How it works: rate limit, constant-time secret check, then the raw JSON body is stored in `integration_events`
(source `leads`, `external_id` = sha256 of `source:source_id`) before anything else. A replay hits the unique index
and answers `duplicate: true`. Then the payload is validated, and the lead is created, linked to duplicates, routed,
matched, logged in `lead_events`, and one email goes to the routed inboxes through `sendEmail` (log-only `skipped`
without `RESEND_API_KEY`). The event is then marked `processed`.

## What the real connectors will need later

- **Google Ads lead forms** (Make 6284112, 7606407): a route that verifies Google's `google_key` from the lead form
  webhook settings, skips `is_test`, maps `user_column_data` (Full Name, User Email, User Phone, product questions) to
  the intake fields, uses `lead_id` as `source_id`, keeps `gcl_id` as `gclid`. Then set `lead_sources.google.active`.
- **Facebook Lead Ads** (Make 8017791, 8082367): a Meta `leadgen` webhook (verify token handshake, `X-Hub-Signature-256`
  HMAC over the raw body with the app secret), then a Graph API call for the lead's fields (needs a long-lived page
  token, stored encrypted like the Xero tokens), `leadgen_id` as `source_id`, `fbclid` when present.
- **Gravity Forms "Product Inquiry"** (form id 2, Make 9892152): the Gravity webhooks add-on posting to the intake
  endpoint with the shared secret header, entry id as `source_id`, GCLID field as `gclid`. This is the `website` source.
- Each connector should add its own source key to `WEBHOOK_SOURCES` or its own route, keep raw-first storage and
  idempotency by source id, and add routing rules plus `leads.<branch>` recipients that mirror the 4 to 6 inboxes
  the Make scenarios email today.
- Later: a routing-rules and recipients editor in Settings, Google offline conversions from stored GCLIDs, inbound
  email-to-lead, and a lead-to-quote-to-invoice funnel report.
