# M3 part 1: Xero write framework and actions (dry run)

Xero is the book of record. Nothing writes to the live Xero organisation until a dry-run diff matches what
Make did. This part builds the framework that enforces that, and the BUILD_PLAN 4.1 to 4.5 actions on top of
it. **Every action defaults to off.**

## What is built

| Piece | Where |
|---|---|
| Run log: one row per action attempt (mode, status, redacted planned requests, effects, expected end state, response summary with ids and status codes only, redacted error) | `supabase/migrations/0007_xero_actions.sql` (`xero_action_runs`: org admins read, only the server writes) |
| The only sender of non-GET requests to the Xero accounting API | `lib/integrations/xero/write/writer.ts` |
| Modes (off / dry_run / live), write-scope check, switch validation | `lib/integrations/xero/write/modes.ts` (pure) |
| Planners, one per action (pure, unit tested) | `lib/integrations/xero/write/plan-*.ts` |
| Redaction for anything stored or printed | `lib/integrations/xero/write/redact.ts` |
| Inputs from the mirror (+ GET refresh in live), runner, effects, outbox handlers | `load.ts`, `run.ts`, `handlers.ts`, `paid.ts` |
| Triggers | `triggers.ts`; hook-ins in `lib/workflow/run-action.ts` (`afterSave`), `lib/integrations/xero/sync.ts` (invoice upserts), `lib/jobs/handlers.ts` |
| Settings page | `/admin/integrations/xero/actions` |

### Actions

| Action (queue `xero.<action>`) | Trigger | Xero writes | Our own effects |
|---|---|---|---|
| `deal.import_quote` (4.1) | DEAL Submit | none (GET quote `QU-{QUOTENO}`) | DEAL `LINE1..8`, `PARTNO1..8` from the quote lines, `Total` from the quote total, via `systemUpdateEntry` (encrypted data, `entry_events` row with actor_role `System`) |
| `rfi.create_invoice` (4.2) | RFI Submit / Update | contact create (PUT) or update (POST); quote status POSTs up to INVOICED; invoice create (PUT) unless one with `Reference == QuoteNo` exists or a line is negative; attachment PUTs (RFI PDF #1 + `_1stDeposit`, `_2ndDeposit`, `_3rdDeposit`, `_4thPayment`) | `external_refs` (`rfi.quote`: quote no -> RFI entry; `rfi.invoice`: invoice id -> RFI entry) |
| `delivery.update_invoice` (4.3) | Delivery Note Submit / Update | invoice Reference = VIN (POST); attachment PUTs (delivery PDF #1, ID, payment 1, payment 2, NATIS, first photo of each of the 4 fields, RFI PDF) | none |
| `release.on_paid` (4.4) | sync/webhook upsert where an invoice's amount due became 0 | none (GET invoice PDF) | RELEASE FORM entry via `runAction` with the `system` actor (Submit, or Update of the mapped entry), `external_refs` (`invoice.release`), email `Release Form - {InvoiceNumber}` to `notification_recipients` `release.paid` with the invoice PDF and release PDF |
| `invoice.merge_attachments` (4.5) | on demand (settings page) | **plan only**: lists downloads, the merged upload `{InvoiceNumber}-merged.pdf`, and originals that could go after the upload | none |

What each one does **in dry run**: loads inputs from the mirror only (no Xero calls at all for the plan),
records the ordered planned requests (redacted) and the expected end state in `xero_action_runs` with status
`planned`, and sends nothing to Xero. Placeholders such as `{{contact}}` and `{{invoice}}` stand for ids that
only a live create would return. Dry run changes nothing anywhere: effects on our own data (the DEAL import
updating the DEAL, the release creating/updating the RELEASE FORM entry and emailing the branches, `external_refs`
mappings) are recorded in the run (redacted) with outcome `dry run: not applied`, and run only in live.

### Modes

- Setting: `app_settings` key `xero.action.<name>`, JSON string `"off" | "dry_run" | "live"`. Missing or
  unknown = **off**.
- **off**: the trigger still enqueues a job; the job records a `skipped` run (reason `mode off`) and stops.
- **dry_run**: as above.
- **live**: requires a connected Xero whose granted scopes include `accounting.transactions`,
  `accounting.contacts` and `accounting.attachments`. If they are missing, the action runs as dry run and the
  run says why. `invoice.merge_attachments` is always plan only. Actions with no Xero writes
  (`deal.import_quote`, `release.on_paid`) need no write scopes for live, but still the typed confirmation.

### Write safety (live)

- `writer.ts` is the only module allowed to send POST/PUT to the accounting API (and the only other fetch
  sites are the GET client and the OAuth token endpoint). `tests/unit/xero-no-writes.test.ts` enforces it.
  There is no DELETE or PATCH, ever.
- Every planned request has a stable step id. In live mode the step is claimed in `action_claims` as
  `<action>:<key>#<step>` (unique per org) before it is sent; `send()` refuses without a claim issued by the
  writer for exactly that request. Idempotency keys: `rfi.create_invoice:<quote no>`,
  `delivery.update_invoice:INV-<no>`, `release.on_paid:<invoice id>`, `deal.import_quote:<entry id>`.
- A completed claim stores its result (status code, captured ids): a retried job reuses it and sends nothing
  (no second contact, invoice or attachment). A 4xx refusal marks the claim `rejected` (nothing was written)
  so a later run may try again. A claim without a result (crash, timeout, 5xx after one resend) stops the
  action with "claim held without result: needs review": a person checks Xero, then removes that claim row.
- Xero's `Idempotency-Key` header (sha256 of org + claim key) is sent on every write. 429 waits Retry-After or
  exponential backoff with jitter; one resend on 5xx under the same key; long waits end the job and the
  outbox retries later with its own backoff.
- In live mode the planner's inputs are re-read from Xero first (GET, upserted into the mirror): the quote,
  the contacts, and invoices with `Reference == QuoteNo`, so a stale mirror cannot cause a second invoice.

### Release trigger

`sync.ts` remembers each invoice's `amount_due` before an upsert. After it, invoices that are now fully paid
(`AmountDue == 0`, sales invoice, status `PAID`, total > 0) and were not paid before enqueue
`release.on_paid`. During the initial backfill, invoices that were never in the mirror do not trigger (old
releases come from the Cognito import in M5); after it, a new invoice that arrives already paid does.
One email per invoice is guarded by the claim `release.on_paid:<invoice id>#email`.

## How to switch an action to live

1. Make sure a Xero **demo company** is connected for rehearsal (never rehearse against the live org).
2. Set `XERO_SCOPES` to the write set and reconnect on `/admin/integrations/xero`:
   `offline_access accounting.transactions accounting.contacts accounting.attachments`
   (`READ_WRITE_SCOPES` in `lib/integrations/xero/config.ts`). The default stays read-only.
3. Run the action in **dry run** next to Make. Export the matching Make executions (read only, inputs and
   requests) into the replay format below and run
   `pnpm tsx scripts/replay-make.ts <file.json>`. Every execution must print `MATCH`
   (BUILD_PLAN M3: 20 RFIs, 20 deliveries, 20 releases).
4. On `/admin/integrations/xero/actions`, choose **live** and type the action name to confirm. This needs
   `xero.actions.configure`; the change is written to `audit_log` (`xero.action.live`, from/to modes).
5. Watch the run log. Switching back to dry run or off is immediate and audited too.

## Replay format (`tt-make-replay/1`)

```json
{
  "format": "tt-make-replay/1",
  "executions": [
    {
      "id": "unique id (e.g. Make execution id)",
      "action": "rfi.create_invoice",
      "scenario": 3191686,
      "entry": { "id": "<entry uuid>", "number": 7, "status": "Submitted", "updatedAt": "<ISO>", "data": { "<FieldName>": "..." } },
      "files": [ { "id": "...", "fieldKey": "_1stDeposit", "kind": "file", "fileName": "...", "contentType": "...", "sizeBytes": 1, "sortOrder": 1 } ],
      "documentName": "REQUEST FOR INVOICE - 7.pdf",
      "today": "YYYY-MM-DD (the day Make ran, for the invoice Date)",
      "xero": { "quotes": [<raw Xero Quote>], "contacts": [<raw Contact>], "invoices": [<raw Invoice>], "attachments": [<raw Attachment>] },
      "rfi": { "entry": { ... }, "documentName": "..." },
      "existingReleaseEntryId": null,
      "ignore": ["Invoices.0.Date"],
      "make": {
        "requests": [ { "method": "POST", "path": "/Quotes/<id>", "body": { ... } }, { "method": "PUT", "path": "/Invoices/<id>/Attachments/<name>" } ],
        "entry": { "LINE1": "...", "Total": 1 }
      }
    }
  ]
}
```

- Inputs only: the Cognito entry payload as Make received it (mapped to field names), and the Xero objects
  Make read, as raw Xero JSON. No tokens, no secrets, no file contents.
- `make.requests`: the Xero requests Make sent, paths relative to `/api.xro/2.0`. Attachment bodies are not
  compared; the file name in the path is.
- `make.entry`: field values Make wrote into a form entry (DEAL import, RELEASE FORM).
- The diff matches requests by method and path (`{{placeholders}}` match any id), then compares JSON bodies.
  Output marks `+ only in platform`, `- only in Make`, `~` changed fields and order changes; personal data
  and uploaded file names are redacted. Exit code 1 when anything differs.
- Recordings hold personal data: keep them out of the repository and delete them after the comparison.

## Assumptions about Xero request shapes (to confirm with the replay)

- Find quote: `GET /Quotes?QuoteNumber=QU-{no}`; contacts: `GET /Contacts?where=EmailAddress=="..."` then
  `Name=="..."`; invoices: `GET /Invoices?where=Type=="ACCREC" AND Reference=="..."`, `GET /Invoices?InvoiceNumbers=INV-{no}`.
- Contact create: `PUT /Contacts` `{Contacts:[{Name, FirstName, LastName, EmailAddress?}]}`. Contact update:
  `POST /Contacts/{id}` with only `FirstName` / `LastName` when they differ from the form (Make's exact update
  fields are unknown).
- Quote status: `POST /Quotes/{id}` `{Quotes:[{QuoteID, QuoteNumber, Contact:{ContactID}, Date, Status}]}`,
  one request per status still ahead (DRAFT -> SENT -> ACCEPTED -> INVOICED; never backwards). Make "posts
  three times with the contact id and the form's name": the name part is not reproduced.
- Invoice from quote: `PUT /Invoices` `{Invoices:[{Type:"ACCREC", Contact, Date: today (org timezone),
  Reference: QuoteNo as typed, Status:"DRAFT", CurrencyCode, LineAmountTypes, BrandingThemeID?, LineItems}]}`
  with line fields Description, Quantity, UnitAmount, ItemCode, AccountCode, TaxType, DiscountRate, Tracking.
  **Status DRAFT is a guess**; no DueDate is sent.
- Set reference: `POST /Invoices/{id}` `{Invoices:[{InvoiceID, Reference}]}`.
- Attachments: `PUT /Invoices/{id}/Attachments/{FileName}?IncludeOnline=false` with the raw bytes and the
  file's content type. One file per Delivery Note field (the first); all files of each RFI deposit field.
- Invoice PDF: `GET /Invoices/{id}` with `Accept: application/pdf`.
- DEAL import writes only the quote's lines (up to 8); lines beyond the quote's count are left as they are.
  A typed `QU-` prefix on QUOTENO is accepted (Make would have looked up `QU-QU-...`).

## Open questions

- **Voided or credited invoices and releases**: should a voided, credited or refunded invoice reverse or flag
  its Release? Today a release fires only on a transition to `PAID`; nothing reverses.
- **Merge attachments needs `pdf-lib`** (not installed; not added). The Xero accounting API has no attachment
  delete, and our rules forbid deleting Xero records: decide whether originals stay (recommended) or the
  Files API is used under an explicit exception.
- New invoice status (DRAFT vs AUTHORISED) and whether Make set DueDate, BrandingTheme or a Title/Summary.
- Which contact fields Make's "update contact" writes, and what "with the form's name" means on the quote POST.
- Does Xero accept a Reference change on PAID invoices (Delivery Note after full payment)?
- Release email sender: Make used a dedicated release address; the mailer has one `MAIL_FROM` today.
- Parallel run: dry run creates no entries and sends no email, so it is safe next to Make. Switch
  `release.on_paid` to live only when Make's release scenario is retired.
- One release email per invoice ever (claim guard). If an invoice is unpaid and paid again, no second email.
- RFI without a 1st deposit: Make still upserts the contact; that optional step is not built.
- Delivery Note when the invoice is not in Xero yet: the job retries with the outbox backoff (5 attempts,
  then `failed`); is a longer wait needed?
