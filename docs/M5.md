# M5: Cognito history import, parallel run, cutover

Part 1 (this document's first half) is the history import. It is built and tested against synthetic fixtures only.
**The Cognito REST shape has not been checked with a real key yet**: work through "API assumptions to verify"
with a dry-run before any `--apply`.

## 1. What the importer does

`scripts/import-cognito.ts` reads every entry of the 7 forms through the Cognito API and writes them into the
platform exactly as the forms engine would have stored them:

| Cognito | Platform |
|---|---|
| Field values, keyed by FieldName | `entries.data[FieldName]` (same shapes as `lib/spec/values.ts`: name `{First, Last}`, address parts, multi-choice arrays, dates `YYYY-MM-DD`, numbers, text) |
| Inspection sub-sections (Fail / Pass / Comments) | `data.checklist[]`, all 20 rows `{itemNo, label, fail, pass, comments}` |
| Delivery Note `QuoteNo` (RFI entry reference) | our RFI entry uuid, found through `external_refs` (RFI is imported first) |
| `Entry.Number` | `entries.number` (set explicitly, so the numbering trigger does not renumber) |
| `Entry.Status` | `entries.status`, matched to the spec's status names |
| `Entry.DateCreated / DateUpdated / DateSubmitted` | `created_at / updated_at / submitted_at` (UTC) |
| Cognito entry id (e.g. `4-123`) | `entries.cognito_entry_id` and `external_refs (source cognito, entity entry:<slug>)` |
| File fields | Storage `entry-files/<form>/<entry-id>/<field>/<uuid>-<name>` + `entry_files` (kind `file`) |
| Signature fields | same path shape + `entry_files` (kind `signature`, file name `<Field>.png`, or `<Field>.svg` for an SVG-only signature, see A7) |
| (import itself) | `entry_events` row: action `Import`, actor_role `Import`, diff = changed field keys only |

- DEAL and Delivery Note data is encrypted with the app's own `sealData` (AES-256-GCM, AAD = entry id): only
  number, status and summary are in clear. The summary is rendered with the form's template (`renderSummary`).
- Nothing is invented. Cognito keys the spec does not know are counted in the report by name and not stored.
  Sub-parts of name/address fields outside the spec (e.g. `Name.Middle`) are reported the same way.
- Values that do not fit are counted under "value issues" (`<field>:<code>`): `invalid_date` (dropped),
  `not_in_options` (kept: a historic option), `not_integer` (kept), `invalid_email` (kept), `truncated` (text over
  10,000 characters, cut like the form would), `checklist_missing`, `checklist_unmatched`, `signature_svg_only`
  (see A7), `file_without_source`, `<field>:file_type_unrecognised` (bytes whose magic number is not an allowed
  type: kept, but stored as `application/octet-stream`, never with the type Cognito declared).
- After each form, `form_counters.last_number` is set to the highest entry number in the form (never lowered),
  so the next platform entry continues after the Cognito numbers.

### Idempotency and crash safety

Per entry, in this order: entries row, then each file (deterministic storage path, upload with upsert, then the
`entry_files` row), then the `Import` event, then the `external_refs` row. The ref is the commit marker:

- An entry with a ref is "already imported" and skipped. A second run imports 0.
- A crash before the ref leaves an entry with `cognito_entry_id` and no ref. The next run reports it as
  "resumable", finds it by `cognito_entry_id`, skips files whose `entry_files` row exists, re-uploads any
  half-written object to the same path, adds the event if missing and writes the ref. Nothing is duplicated
  (the unit test crashes the run after 1, 2, 5, 9, 17 and 40 writes and compares with a clean run).
- A file that cannot be downloaded or stored fails the entry (`failed: download_failed | upload_failed |
  file_too_large`), which stays resumable. Fix the cause and re-run.
- An entry number already used by a platform entry that is not this Cognito entry is reported as
  `failed: number_taken` and never overwritten. **Import before the platform takes live entries** (section 5).

### Reasons in the report

| Reason | Meaning |
|---|---|
| skipped `unknown_status` / `missing_status` | `Entry.Status` is not one of the form's statuses (or empty); add a mapping before importing |
| skipped `missing_number` / `missing_timestamps` | the entry has no Entry.Number / no dates |
| skipped `lookup_unresolved` | Delivery Note whose RFI entry is not imported (deleted in Cognito, or RFI not run yet). `--allow-unresolved-lookups` imports it with the lookup empty |
| skipped `before_since` | created before `--since` |
| failed `number_taken` | number already used by another platform entry |
| failed `download_failed` / `upload_failed` / `file_too_large` / `write_failed` | see above; entry stays resumable |

## 2. Getting a Cognito API key

1. Sign in to Cognito Forms as an owner of org `trailersandtankers1`.
2. Organization settings → Integrations → API (check the plan includes API access; BUILD_PLAN says it is available).
3. Create an API key with **read** access to entries and files of the 7 forms (no write scope is needed: the
   importer only reads). Note its expiry.
4. Put it in `.env.local` as `COGNITO_API_KEY=...` on the machine that runs the import. Never commit it or paste
   it into a ticket. Remove the key from Cognito and from `.env.local` after cutover (BUILD_PLAN section 9).

## 3. Running it

Requirements in `.env.local` (or the shell): `COGNITO_API_KEY`, `NEXT_PUBLIC_SUPABASE_URL`,
`SUPABASE_SERVICE_ROLE_KEY`, `ENTRY_ENCRYPTION_KEY` (the production key: data encrypted with another key cannot
be read by the app), and `ORG_ID` if the project has more than one org. The script runs with
`tsx --conditions=react-server` so it can import the app's server-only `sealData`.

```bash
# 0. Back up the database (Supabase dashboard: Database -> Backups) before the first apply.

# 1. Dry-run everything. Reads Cognito and the platform, writes nothing, prints counts only.
pnpm import:cognito --form all --dry-run
pnpm import:cognito --form all --dry-run --json > import-dry-run.json   # counts only, safe to share

# 2. Check: "seen" vs the expected counts (DEAL 550, RFI 1,345, Release 1,525, Delivery Note 1,095,
#    Inspection 690, Store Room 8; Job Card unknown), "unknown fields" (should be none, or explained),
#    "value issues", skipped reasons, and that file counts/bytes are plausible.
#    Fix assumptions (section 6) in lib/import/cognito/api.ts or map.ts and repeat until clean.

# 3. Small apply per form, then spot-check those entries (section 4).
pnpm import:cognito --form request-for-invoice --apply --limit 30
pnpm import:cognito --form delivery-note --apply --limit 30

# 4. Full apply (re-runs skip what is done; safe to repeat after an interruption).
pnpm import:cognito --form all --apply

# 5. Re-run the dry-run: every form must show "to import: 0" and "failed: 0".
pnpm import:cognito --form all --dry-run
```

Other options: `--since YYYY-MM-DD` (only entries created on or after; used for the final catch-up before
cutover), `--list-mode list` (use the list endpoint, A3), `--max-number N`, `--concurrency N` (default 4).
The exit code is 2 when any entry failed.

Without Supabase env, a dry-run runs offline against the kit specs (useful to check the API with the key alone);
it cannot tell what is already imported or detect number clashes.

The output never contains names, emails, ID numbers, file names or field values: only form slugs, Cognito field
names, reason codes and counts. Do not add logging of entry data to the script.

After a full apply, rebuild the deal files so imported entries are linked: enqueue the `deal-files.rebuild` job
(`lib/jobs/handlers.ts`, `rebuildDealFiles`); the next scheduled Xero sync also enqueues it when anything changed.

## 4. Spot-check procedure (30 entries per form, including files)

For each of the 7 forms (all entries for Store Room, which has 8):

1. Pick 30 entry numbers spread over the range: the 5 oldest, the 5 newest, 20 random; include at least 3 with
   files/signatures and, for Inspection, entries in each status (Submitted, Reviewed, Approved).
2. Open the entry in Cognito and at `/admin/forms/<slug>/entries/<number>` side by side and check:
   - number, status, created and submitted dates (platform shows Africa/Johannesburg; Cognito shows UTC);
   - every field value, including name and address parts, multi-choice options, dates, numbers;
   - Inspection: all 20 checklist rows, especially items 1 and 11 (they share the Cognito name `Pass`);
   - Delivery Note: the Quote no lookup shows the right RFI customer panel;
   - files: same count per field, each opens, same size; signatures render (all 5 on a Delivery Note);
   - DEAL and Delivery Note: generate the PDF and compare with Cognito's document.
3. Record results per form (entry number, OK / issue) in the cutover checklist. Do not paste customer data
   into tickets or chat; refer to entry numbers.
4. Any mismatch: fix the mapper, then delete only the affected imported entries (admin, by number) together
   with their `external_refs` rows, and re-run the import for that form.

Acceptance (BUILD_PLAN M5): import counts match Cognito, the 30-entry spot checks match including files.

## 5. Parallel run and cutover

From BUILD_PLAN M5. Make stays live throughout; the platform runs alongside it.

1. **Order matters**: run the history import (section 3) before the platform takes any live entry, so imported
   numbers do not clash with new ones and `form_counters` continue after Cognito's numbers.
2. **Parallel run**: Make stays live and forwards source events to the platform in test mode; a nightly parity
   report compares what Make did with what the platform would do. Catch up entries created in Cognito during
   the parallel run with `--since <date of the last run>` (already-imported entries are skipped). Note that an
   entry edited in Cognito after it was imported is not re-imported: the importer never overwrites; delete and
   re-import that entry if needed.
3. **Cut over in this order**: forms intake, Deal, RFI, Delivery Note, Release.
4. **Retire each Make scenario only after two clean weeks** for that step. Clone the scenario first and keep a
   ROLLBACK COPY. **Never edit, activate or delete an active scenario in place** (CLAUDE.md rule 11: this repo
   only reads Make).
5. Switch public links, QR codes and website buttons to `/f/<slug>` on the production domain. Verify the Resend
   domain (SPF, DKIM).
6. After the last form is cut over: run a final `--since` catch-up and dry-run (to import 0), turn the Cognito
   forms off, revoke the Cognito API key and remove `COGNITO_API_KEY`.

Done when: import counts match Cognito, spot checks of 30 entries per form match including files, two clean
weeks, Make scenarios off.

## 6. API assumptions to verify with a real key

None of these has been confirmed against Cognito. The tag (A1..A13) is repeated in code comments. Verify each
with a dry-run (`--limit 5`) and, where needed, by fetching one entry by hand with curl and looking at its JSON
on the operator's machine (never paste real entry JSON into a ticket or a test fixture).

| # | Assumption | Where | How to check / what to change |
|---|---|---|---|
| A1 | Base URL `https://www.cognitoforms.com/api`, header `Authorization: Bearer <key>` | api.ts | A 401/403 on the first call means the auth scheme or key scope differs |
| A2 | `GET /forms/{formId}/entries/{entryNumber}` returns one entry; 404 for a deleted/missing number; `{formId}` accepts the numeric form id from the spec (4, 5, 6, 8, 9, 12, 13) | api.ts `listEntries` (default `by-number`) | If 404 everywhere, try the internal name (`RequestForInvoice`) or entry id `4-1` in the path |
| A3 | A list endpoint `GET /forms/{formId}/entries?skip=&take=` exists (only with `--list-mode list`) | api.ts `listPaged` | Optional. If it exists, it is faster; adjust paging parameter names |
| A4 | Entry JSON: id in `Id` (`"<formId>-<number>"`), metadata in `Entry` (Number, Status, DateCreated, DateSubmitted, DateUpdated), form info in `Form`; other top-level keys are FieldNames | map.ts `META_KEYS`, `mapEntry` | Unknown metadata keys show up in "unknown fields"; add them to `META_KEYS` |
| A5 | `Entry.Status` holds the workflow status name (Incomplete, Submitted, Reviewed, Approved, APPROVAL, APPROVED EMAILED) | map.ts `mapStatus` | `skipped: unknown_status` counts; add a mapping if Cognito returns other names |
| A6 | File fields are arrays of `{Id, Name, ContentType, Size, File}` where `File` is a URL readable with the bearer key; or `GET /files/{Id}` returns the bytes or JSON with a download URL | map.ts `fileRefs`, api.ts `downloadFile` | Dry-run file counts/bytes; apply `--limit 1` and open the file. The bearer key is only sent to `*.cognitoforms.com`. A `File` URL that is not an https Cognito URL is not fetched: the file is downloaded through `GET /files/{Id}` when it has an `Id`, else it fails |
| A7 | Signatures are objects with `Png` (URL or `data:image/png` URL) and/or `Svg` markup, or file-like | map.ts `signatureRef` | `signature_svg_only` counts mean no PNG was available. The inline SVG is stored as `image/svg+xml` (renders in `<img>`; the PDF renderer may not draw it) only when `safeSignatureSvg` (lib/security/files.ts) accepts it: an `<svg>` root with drawing elements only, no script, foreignObject, `on*=`, `href`/`xlink:href`, DOCTYPE/ENTITY, `url(`. Otherwise it is stored as `application/octet-stream` and counted as `file_type_unrecognised`. Check whether Cognito offers a PNG |
| A8 | Entry timestamps are ISO strings; without an offset they are UTC (Cognito org timezone is UTC) | values.ts `toTimestamp` | Compare created dates of a spot-check entry |
| A9 | Date fields come as `YYYY-MM-DD` (or ISO date-time); US `M/D/YYYY` accepted as fallback | values.ts `toDate` | `invalid_date` counts |
| A10 | Name sub-keys First/Last (+ derived FirstAndLast etc.), address sub-keys Line1, Line2, City, State, PostalCode, Country (+ FullAddress, Type, Latitude, Longitude) | values.ts `DERIVED_PARTS` | Reported as `Name.<x>` / `Address.<x>` unknown fields |
| A11 | Inspection sub-sections are nested objects (under `TrailerInspectionResults` or top level), each holding its own Fail/Pass/Comments keys | checklist.ts | `checklist_missing` / `checklist_unmatched` counts, and spot-check items 1 and 11 |
| A12 | The Delivery Note `QuoteNo` lookup value is the RFI entry id (`"4-123"`), an object with `Id`, or the entry number | map.ts `lookupExternalId` | `lookups unresolved` and `invalid_value` on QuoteNo |
| A13 | Rate limits unknown; 429/5xx are retried with backoff and `Retry-After` | api.ts `request` | Lower `--concurrency` if 429s persist |

Also check with the dry-run: the Delivery Note table key (`QuoteNoNameQuoteNoNameFirst...`) is recognised by its
prefix and not stored; whether Job Card is still used (its count was unknown at export).
