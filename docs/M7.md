# M7: Users, access levels and activity log

Asked for: invite users, edit them, set an access level per menu (no access / read / write), and an activity
(history) log. Today there is one admin and fixed roles (`admin`, `staff`, `reviewer`, `inspector`, `factory`
from M6) with a hard-coded permission list in `lib/security/can.ts`.

## 1. Access model

- **Areas** = the menus: `home`, `tasks`, `forms`, `deals`, `quotes`, `invoices`, `leads`, `stock`,
  `integrations`, `settings`, `users`, `activity`. Each user has a level per area: `none` | `read` | `write`.
- **Admin** (role `admin`) has write everywhere plus the admin-only actions below. At least one active admin
  must always exist (enforced in the server action and in SQL).
- **Presets** (the existing roles) fill the per-area levels when chosen; any area can then be changed, which
  marks the user "Custom". The resolved map is always stored, so SQL never needs the preset table.

| Preset | home | tasks | forms | deals | quotes | invoices | leads | stock | integrations | settings | users | activity |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| admin | all write (and admin-only actions) |||||||||||
| staff | read | read | write | read | read | read | write | write | none | none | none | none |
| reviewer | read | read | read | read | read | read | none | read | none | none | none | none |
| factory | read | none | none | none | none | none | none | write | none | none | none | none |
| inspector | none (role links only) |||||||||||

- Permissions keep their names (call sites unchanged); each maps to `(area, level)` or admin-only:
  `admin.access` = any area >= read; `forms.read`/`entries.read`/`entries.export` = forms read;
  `entries.write` = forms write; `entries.review`/`entries.approve` = forms write AND preset reviewer/admin
  (workflow approval stays a role, not a menu); `tasks.read` = tasks read; `xero.read` is split into
  `deals.read`, `quotes.read`, `invoices.read` at the call sites; `leads.read`/`leads.manage` = leads read/write;
  `stock.read`/`stock.export` = stock read, `stock.dispatch` = stock write; `integrations.manage` = integrations
  write; `settings.manage`/`forms.manage` = settings write; `users.manage` = users write; `audit.read` =
  activity read. Admin-only: `entries.delete`, `xero.actions.configure`, `import.run`, `stock.manage`.
- Disabled or invited (not yet accepted) members have no access at all.
- **Database enforcement**: `public.has_access(p_org, p_area, p_level)` (security definer, reads the caller's
  membership) and RLS select policies use it per table: entries/entry_* = forms, deal_files = deals,
  xero_quotes/lines = quotes, xero_invoices/lines/payments/attachments = invoices, leads/lead_events = leads,
  stock_* = stock, audit_log = activity, memberships (other users) = users. So a user with "none" cannot read
  the data through the API either, not just in the UI.

## 2. Data (migration 0014_access.sql)

`memberships`: `display_name`, `access jsonb` (resolved area -> level), `preset text`, `status`
(`invited` | `active` | `disabled`), `invited_by`, `invited_at`, `accepted_at`, `disabled_at`, `last_seen_at`.
Backfill: existing members `active`, access from their role preset. Clients cannot write memberships; changes
go through server actions (users.manage) that write `audit_log`. A trigger refuses removing or disabling or
demoting the last active admin of an org.

## 3. Screens (Settings, tabs; design tokens only)

- **Organisation** (existing).
- **Users & access**: list (name, email, preset or Custom, status, last sign-in, last seen); **Invite user**
  (email, name, preset, per-area levels, optional branch) -> Supabase invite email (`auth.admin.inviteUserByEmail`,
  redirect to `/auth/confirm`), plus **Copy invite link** (`generateLink`) because email delivery may not be set up;
  **Edit** (name, preset, per-area matrix of None/Read/Write radio buttons, branch); **Resend invite**;
  **Disable / Enable** (disabled users are also banned in Supabase Auth so their sessions stop);
  **Remove from organisation** (keeps their history). Admins cannot lock themselves out.
- **Activity log**: every `audit_log` row for the org, newest first, filters (user, area, action, date range,
  search entity id), 50 per page, CSV export (audited); each row in plain words with a link to the record.
  Includes sign-in / sign-out / failed sign-in (no password or email in meta), user and access changes,
  settings, form settings, exports, deletes, Xero, leads, stock.
- **User detail**: the user's access matrix and their own history (activity filtered by actor), sign-in history.
- **Forms** (existing).
- **My account** (`/admin/account`, every user): name, change password, own recent activity.
- Accept flow: `/auth/confirm` (verifies the token hash) -> `/admin/account/password` (set password) -> `/admin`.
- Nav, phone tabs, search and home tiles show only areas the user can read; pages call `requirePerm` as today.

## 4. Acceptance

Invite -> accept -> set password -> sign in sees only allowed menus; read-only areas show no write buttons and
server actions refuse writes; a user with `none` gets 403 on the page and empty results from the API (RLS);
disable stops access immediately (next request); last admin cannot be removed/disabled/demoted; every user and
access change, sign-in and export appears in the activity log with the actor; cross-org isolation unchanged.

## 5. Built (M7)

### Access model (`lib/security/can.ts`, pure, `tests/unit/can.test.ts`)

- `AREAS`, `LEVELS`, `PRESET_ACCESS` (the table in section 1), `clampAccess(role, map)` (admin = all write; unknown
  values = none; factory ceiling), `presetOf(role, map)` (the preset name or `custom`), `canArea(member, area, level)`.
- `Member` gains `access` (resolved map) and `status`. `getMember()` always fills both from `memberships`; a Member
  built from a role only (tests, scripts) gets the role's preset and counts as active.
- `can()` refuses everything unless `status = 'active'`. Admin (role `admin`) passes every rule; the admin-only
  permissions need role admin. Every other permission resolves through `RULES`:

| Permission | Needs |
|---|---|
| `admin.access` | any area at read or better |
| `home.read` | home read |
| `forms.read`, `entries.read`, `entries.export` | forms read |
| `entries.write` | forms write |
| `entries.review`, `entries.approve` | forms read **and** role reviewer or admin |
| `tasks.read` | tasks read **and** forms read |
| `deals.read` / `quotes.read` / `invoices.read` | deals / quotes / invoices read |
| `leads.read` / `leads.manage` | leads read / write |
| `stock.read`, `stock.export` / `stock.dispatch` | stock read / write |
| `stock.invoices` | stock read **and** invoices read |
| `integrations.read` / `integrations.manage` | integrations read / write |
| `settings.read` / `settings.manage`, `forms.manage` | settings read / write |
| `users.read` / `users.manage` | users read / write |
| `audit.read` | activity read |
| `entries.delete`, `xero.actions.configure`, `import.run`, `stock.manage` | admin only |
| `xero.read` (deprecated) | quotes read **and** invoices read; no call site uses it any more |

- Factory ceiling: a member whose role is `factory` never gets tasks, forms, deals, quotes, invoices or leads, whatever
  the map says (0011's restrictive `*_not_factory` policies stay and agree). Choose another preset to give more.
- `requirePerm()` answers 403 with `forbidden()` (`experimental.authInterrupts`, page `app/forbidden.tsx`).

### Database (`supabase/migrations/0014_access.sql`, `tests/db/access.test.ts`)

- `memberships`: `display_name`, `access` (checked by `valid_access()`), `preset`, `status`
  (`invited | active | disabled`), `invited_by`, `invited_at`, `accepted_at`, `disabled_at`, `last_seen_at`, `must_change_password` (Add user).
  A before-insert/update trigger fills `access` from the role's preset when missing (create-admin, older inserts),
  clamps it (`clamp_access()`, same rules as `clampAccess`) and sets `preset`. Backfill: every existing member active
  with their role's preset.
- `has_access(org, area, level)` (security definer): active member, admin or the stored level. `is_org_member()`
  and `has_org_role()` now also require `status = 'active'`, so invited and disabled members read nothing at all.
- Read policies per area: entries, entry_files/events/documents, email_log, entry_reads (own) = forms;
  deal_files = deals; xero_quotes/lines = quotes; xero_invoices/lines/payments/attachments = invoices;
  xero_contacts = quotes or invoices; xero_sync_state = integrations; leads/lead_events/lead_sources = leads;
  stock_* = stock (stock_invoice_exceptions = stock and invoices); notification_recipients = settings;
  audit_log = activity (plus `stock.*` rows with stock read, and every member's own rows); memberships and
  profiles of other members = users. Client writes to orgs, form definitions, recipients and app_settings need
  settings write (the 0009/0011 locks on `xero.action.*` and `stock.*` keys stay).
- `memberships_last_admin` trigger: refuses removing, disabling or demoting the last active admin of an org
  (`LAST_ADMIN`; serialised per org with an advisory lock).
- `stock_require_role()` (used by the stock RPCs) follows the map: admin-only RPCs stay admin-only, dispatch/move need
  stock write, inactive members are refused.

- Nav, phone tabs, home tiles and search show only readable areas. Settings shows when any of its tabs is readable.
  Search routes quote/invoice numbers only to readable lists, else deal files, else the stock register; no readable
  area means no search box. Home needs home read; without it `/admin` opens the first readable menu.
- Invited members who open the admin are sent to the set-password page; disabled members see "access disabled".

### Add user (temporary password)

- Besides Invite, **Add user** creates the account directly: `auth.admin.createUser({ email, password, email_confirm: true })`,
  membership `active` with `must_change_password = true`. No email is sent; the admin passes the temporary password on.
  A generated password (16 characters, no look-alikes, Web Crypto) is shown once on the result screen and never stored
  or logged. An email that already has an account is refused ("use Invite user instead").
- Until they change it, `requirePerm()` and the admin layout send the member to `/admin/account/password`
  ("Choose a new password"; no current password asked, they just signed in with it). Saving clears the flag and
  audits `auth.password` with `{ first: true }`.
- Audited `user.add` (preset, access map, generated yes/no): never the email or the password. Only admins may add an
  admin. mini-supabase serves `POST /auth/v1/admin/users` (createUser).

### Users & access rules (`lib/users/rules.ts`, pure, `tests/unit/users.test.ts`)

- Nobody changes their own preset, access or status, or removes themselves (`self`); the Edit page shows their own
  matrix locked.
- Only an admin invites, changes, disables, enables or removes an admin account (`admin_only`): a member with Users
  write cannot reach the admin-only actions by making an admin. Users write is still powerful (it can grant any
  non-admin level), so give it to trusted people only.
- The org keeps one active admin (`last_admin`), checked in the action and by the trigger.
- Disable: status disabled + banned in Supabase Auth (`ban_duration 876000h`) so refresh tokens stop; the next request
  is refused by the membership status anyway. Enable: back to active (or invited if never accepted) and unbanned.
  Remove: deletes the membership only (the account and its history stay) and lifts a Disable ban.

### Activity log (`lib/activity/describe.ts`, pure)

- Areas by action prefix (`user.`/`auth.`/`admin.` = users, `entry.`/`entries.` = forms, `lead.` = leads,
  `stock.` = stock, `xero.` and the M3 action names = integrations, `settings.`/`form.` = settings, `audit.` = activity).
- Plain words with member names (names from memberships/profiles via the service role after audit.read; rows hold
  ids only). Unknown actions render generically. Links only for well-formed ids.
- New audit actions: `auth.sign_in` (meta method password|link), `auth.sign_out`, `auth.sign_in_failed` (entity user =
  the account id when the email belongs to a member, else entity `auth` in the default org; never the email),
  `auth.password`, `user.invite` (preset, access, method), `user.invite_link`, `user.invite_resend`, `user.accept`,
  `user.update` (preset/role from-to, `changes` [area, from, to], name/branch changed flags), `user.disable`,
  `user.enable`, `user.remove`, `user.name`, `user.add`, `audit.export`. Links and tokens are never audited.

### Assumptions and open questions

- Approval: the preset table gives reviewers forms read, so `entries.review`/`approve` need forms **read** (not write)
  plus the reviewer or admin role; otherwise no default reviewer could approve.
- Tasks need forms read too (every task opens an entry). The matrix says so next to Tasks.
- `stock.export` now follows stock read (as the permission list in section 1 says), so reviewers and factory
  accounts can export the stock register; M6 had it for admin and staff only. Confirm.
- Members with only Users or Activity access see Settings with just those tabs.
- Branch is optional, chosen from the org's non-factory stock locations; nothing filters by it yet.
- Last sign-in comes from `auth.sign_in` audit rows (so it starts with M7), not from Supabase Auth.
- One org per user today: the session uses the member's first membership; Disable bans the whole Auth account.
- Passwords: at least 10 characters; changing one asks for the current password.
